# Power management on MacBookPro16,1

These notes describe measurements made on a 2019 16-inch Intel/T2 MacBook Pro
running Omarchy/Arch and `linux-t2` kernel
`7.1.8-arch1-Watanare-T2-3-t2`. They are observations from this machine, not a
universal recipe for every T2 Mac.

## Short version

Use separate boot entries and reboot when the workload changes:

| Mode | Use it for | Observed draw |
| --- | --- | --- |
| AMD/default | Games, 3D work, external-display or GPU-heavy sessions | About 33--37 W at light load before tuning; occasional readings near 63 W |
| Intel battery | Browsing, editing, terminals, and time away from AC | 15.98 W controlled screen-on baseline at 50% brightness |

The Intel result is a real improvement of roughly 17--21 W. It is still above
the approximately 9 W sometimes reported for an ideal T2 Linux setup because
the Intel display path on this machine is missing important low-power features.

Do not interpret a monitoring application's `GPU: 0 W` as proof that the AMD
GPU is off. Confirm its mux and PCI power states as described below.

## What caused the original drain

The primary culprit was the Radeon Pro 5500M remaining powered because it was
driving the internal panel. At apparent idle it was in PCI D0, its GDDR6 memory
was running around 736 MHz, the board sensor reported approximately 16--19 W,
and the GPU temperature was 67--69 C. CPU package power was only around 3.5 W,
so CPU tuning could not account for the 33--37 W battery drain.

The Intel-mode test changed the topology successfully:

- Intel UHD 630 drives `eDP-1`.
- `vgaswitcheroo` reports `DIS:Off` for `0000:03:00.0`.
- The Radeon is in D3hot and its HDMI-audio function is in D3cold.
- The AMD kernel log still says `Runtime PM not available`; explicit early
  switch-off is therefore important.

## Known-good boot arrangement

Keep the existing/default `linux-t2` entry unchanged. Duplicate it under a
clearly named entry such as `linux-t2 (Intel graphics test)` and add only:

```text
apple_gmux.force_igd=1
```

The Intel entry on this machine is paired with an early systemd service whose
unit has this safety condition:

```ini
ConditionKernelCommandLine=apple_gmux.force_igd=1
```

The service waits for `/sys/kernel/debug/vgaswitcheroo/switch`, writes `OFF`,
and verifies that the discrete GPU reports `DIS:Off`. The condition matters:
it prevents the service from powering off the GPU that owns the panel in the
normal AMD entry.

The default AMD entry is the recovery path. If the Intel entry ever produces a
black screen, force a shutdown only if the machine cannot be reached another
way, then choose the unchanged AMD entry from the boot menu. Do not replace the
only known-working entry while experimenting.

## Battery-mode policy used here

Only when `apple_gmux.force_igd=1` is present, a local oneshot policy applies:

- `powerprofilesctl set power-saver`
- Intel GPU maximum frequency of 600 MHz
- Wi-Fi power saving on
- Bluetooth soft-blocked
- Hyprland animations disabled

The normal AMD entry restores balanced mode, the Intel GPU's default maximum,
Wi-Fi power saving off, Bluetooth enabled, and normal desktop animations.

NetworkManager also created a misleading Ethernet profile for the T2
controller's internal `cdc_ncm` interface. It saw carrier and retried DHCP every
45 seconds. Its autogenerated `Wired connection 1` profile was set to
`connection.autoconnect=no`. This does not turn off the T2 controller; it only
stops NetworkManager from treating the controller's internal USB-network
function as a LAN connection.

## Verification

Confirm the selected boot mode:

```bash
grep -o 'apple_gmux.force_igd=1' /proc/cmdline
```

Confirm GPU ownership and power state (the switch file normally requires root):

```bash
sudo cat /sys/kernel/debug/vgaswitcheroo/switch
cat /sys/bus/pci/devices/0000:03:00.0/power/runtime_status
cat /sys/bus/pci/devices/0000:03:00.0/power_state
```

Expected Intel-mode results include `IGD:+:Pwr`, `DIS: :Off`, and Radeon
`D3hot`. Also check the policy:

```bash
powerprofilesctl get
iw dev wlp5s0 get power_save
rfkill list bluetooth
```

Battery watts can be calculated on this battery driver, which does not expose
`power_now`, from current and voltage:

```bash
awk -v c="$(cat /sys/class/power_supply/BAT0/current_now)" \
    -v v="$(cat /sys/class/power_supply/BAT0/voltage_now)" \
    'BEGIN { printf "%.2f W\n", c * v / 1e12 }'
```

Take multiple readings after the chassis cools. UPower's `energy-rate` is a
useful cross-check but is averaged and can lag workload changes.

## Why the remaining draw is about 16 W

The controlled baseline paused the active Codex terminal UI, left the screen on
at 50%, and collected eight samples over 40 seconds:

```text
mean 15.976 W, minimum 15.753 W, maximum 16.358 W
```

With Codex actively updating inside Ghostty, the same system drew about 23 W.
Pausing Codex raised Intel GPU RC6 residency from roughly 20--30% to roughly
60--70%, showing that frequent terminal repainting has a surprisingly large
cost. Freezing Quickshell alone made no meaningful difference.

The remaining platform floor has several contributors:

- The kernel reports `Failed to find VBIOS tables (VBT)` for i915.
- Panel self-refresh status cannot be read because the feature is unavailable.
- Framebuffer compression says `FBC enabled` but `Compressing: no`.
- DMC firmware is loaded, but DC5/DC6 entry counts remain zero.
- Apple firmware declares no OS support for PCIe ASPM.
- The T2 NVMe, BCE core/audio, internal xHCI, and Broadcom Wi-Fi remain active
  in D0. Some are required for storage, keyboard/trackpad, Touch Bar, or audio.
- The LCD was at 49% (`32112/65535`) brightness during the final measurement.

The CPU is not the dominant residual load: `intel_pstate` uses the powersave
governor, its energy-performance preference is `power`, idle frequency reaches
about 800 MHz, and C8/C9/C10 states are available and observed.

## Why live switching is not the default recommendation

In principle, `vgaswitcheroo` can switch muxed GPUs. In practice, this model's
internal panel, Apple gmux implementation, DRM clients, and unavailable AMD
runtime PM make a live transition fragile. A compositor or browser retaining a
DRM file can prevent shutdown; a failed panel handoff can leave no local display;
and suspend/resume on this model already has kernel-version-specific issues.

A logout-and-switch scheme would still require stopping the entire graphical
session and carefully reprobling devices. It saves little time compared with a
reboot and has a worse recovery story. Treat it as future experimental work,
not a daily-use feature.

## Further experiments, in priority order

1. Lower the panel brightness when endurance matters. This is safe and directly
   reduces panel/backlight power.
2. Reduce continuously animated or rapidly updating terminal/browser content.
   The measured difference in this session was about 6--7 W.
3. Test a separate, disposable Intel boot entry with current T2-community i915
   recommendations such as GuC firmware enablement. Keep both known-good entries.
4. Investigate obtaining a correct model-specific Intel VBT so PSR/FBC/display
   C-states can work. This is advanced and carries a real black-screen risk.
5. Revisit runtime PM as T2 BCE/audio and hybrid-graphics patches evolve.

Do not force `pcie_aspm=force` casually. Firmware explicitly disables ASPM on
this machine, and forcing it can destabilize the T2, NVMe, Wi-Fi, or Thunderbolt
paths. Do not autosuspend arbitrary T2 USB devices: they include the keyboard,
trackpad, Touch Bar, ambient-light sensor, and headset interfaces.
